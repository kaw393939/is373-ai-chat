## Trigger and scope

The existing [verification run 40429851400](https://github.com/kaw393939/is373-ai-chat/actions/runs/40429851400) stopped at the vulnerability gate with `certifi==2026.7.22`. [GHSA-6q48-6c7w-9gw2](https://github.com/advisories/GHSA-6q48-6c7w-9gw2) describes compromised intermediate keys beneath an emSign trust root. An on-path attacker could impersonate TLS hosts to clients trusting that bundle. The advisory recommends certifi 2026.10.19 or later and rebuilding images that vendor it. A finding establishes exposure, not evidence of exploitation.

The reviewed change updates only certifi's package entry in [`uv.lock`](../../uv.lock) to **2026.10.23** and assigns the unused compatible patch version **2.0.1** in [`VERSION`](../../VERSION). Official [PyPI release metadata](https://pypi.org/project/certifi/2026.10.23/#files) matches the locked source and wheel hashes. Certificate and hostname verification stay enabled. No database migration or application feature change is intended.

Host package maintenance does not replace dependencies inside an existing image. This fix requires rebuilding and selecting a new image. Python **3.14.7** and build tool uv **0.12.15** remain unchanged; broader Python/build-tool trust scope is tracked separately in [issue #45](https://github.com/kaw393939/is373-ai-chat/issues/45).

## Check the change, then the release

The [TLS probe](../../tests/process/check_tls_trust.py) inspects the actual certifi bundle and exercises local TLS connections, using disposable certificates without an external provider or paid key. Its source run passed: compromised G3 absent, unaffected G1 retained, trusted matching peer accepted, untrusted issuer rejected (code 20), and wrong hostname rejected (code 64). The probe also rejected the authentic old bundle and a fixture that incorrectly removed G1. Temporary certificates/server were cleaned. These local checks are not yet exact-image CI evidence.

Valid trust must succeed; invalid trust and hostname cases must fail. These are positive and negative **cases**. Unit, integration, process and browser checks describe different **levels**; a negative test is not a separate level. The CI probe runs with no external network, a read-only root, bounded resources and temporary writable `/tmp`; promotion requires its report to match the selected candidate's commit/version.

Keep the existing quality, coverage, browser, vulnerability, SBOM and process checks. A scan reports known findings under its database and policy at a particular time; passing does not mean zero vulnerabilities. Synthetic TLS checks do not reproduce the compromised CA's private keys or establish that every outbound client uses the same trust store.

Follow the [release contract](../decisions/0001-environments-and-releases.md) and [promotion runbook](../install-and-delivery.md): build once, test that image, publish it, verify its digest in development and QA, then explicitly select that same digest for production through the existing owner-reviewer gate. Dispatch and approval are separate controls. Do not weaken the gate or relabel an existing release. A source diff, passing scan or merged PR alone does not prove running containers are patched.

## What IS373 students can learn

Ask which layer owns the vulnerable package, what exact artifact each check ran, and what observation proves deployment. The useful process is small and visible: explain the requirement, make a scoped change, let deterministic tools challenge it, inspect the evidence, then approve and verify the release. Preserve the failed gate as part of the explanation rather than hiding it. Close issue #44 only when its required runtime evidence is linked; keep remaining scope in its own issue.
